# Chat 办公能力验收与 ChatGPT 功能对齐

日期：2026-11-06。当前对象：单插件候选版 `dsh-beluga 0.1.0`，未修改的 DSH `0.2.1-rc.3`。

## 结论：聊天基础可用，原生 Office 工作流尚未接入

当前插件可以上传、保管和下载 Word／PPT／Excel 原文件，但不能原生读取三种文件内容，也没有生成、编辑或预览办公产物的工具。PDF／CSV／TXT 可读。当前的“下载文件”下载的是用户上传的原件，不能当作已修改的输出。

推荐方向：保留一个插件、一个无须选仓库的 Chat 入口，增加完整办公工作流，而不是增加三个只能聊天的入口。优先完成 **上传 → 结构化理解 → 生成或定点修改 → 校验与预览 → 下载可编辑文件 → 继续修改**。

## ChatGPT 对标应覆盖交付物，而不只是回答

当前 OpenAI 官方网页指南把文档、表格和演示文稿等多步任务放在 **Work**，Chat 主要用于问答交流。我们可以继续把个人办公放在本插件的 Chat 中；不必照搬模式名称，也不应要求用户转进 coding Work。[官方网页指南](https://learn.chatgpt.com/docs/web)

办公对齐的主要依据：

- 可创建、预览、下载文件，并对指定页面、幻灯片、工作表或段落继续修改。[文件工作流](https://learn.chatgpt.com/docs/artifacts-viewer)
- 从笔记或已有材料形成文档，再从文档生成演示稿；支持参考样式和可复用模板。[文档与演示稿流程](https://learn.chatgpt.com/training/walkthroughs/create-slides-and-docs)
- 演示稿要尽量保留可编辑文字、图表和版式，按渲染结果检查，而不止交付大纲。[生成或修改演示稿](https://learn.chatgpt.com/use-cases/generate-slide-decks)
- 表格应交付可编辑 `.xlsx`，保留原始数据、使用公式、核对汇总和分类，并允许继续修改。[预算与实际对比](https://learn.chatgpt.com/use-cases/budget-vs-actuals-review)

这些是官方文档说明的能力；本轮没有使用用户的 ChatGPT 账户发起模型任务，也没有把不同套餐或桌面加载项功能当作已验证的网页权益。

## 当前验收结果

执行主机：Desktop / Linux x86_64 / Node 24.22.1；界面检查：Mac Chrome。产品源码未修改。所有新输入均为合成业务材料，不包含真实导出或办公资料。

- 原有 **35 个回归测试全部通过**。
- 新增 **14 个办公探针**：6 项可用、6 项明确缺失、2 项隐私／权限保护通过。探针成功复现缺口不等于缺失功能通过验收。
- 探针调用真实已构建插件、Cordis 服务和文件接口；只脚本化模型工具调用，不评价模型理解或写作质量。

| 测试 | 结果 | 实际观察 |
|---|---|---|
| DOCX／XLSX／PPTX 上传与下载 | 可用，3 项 | 原始字节一致；当前 MIME 为通用二进制 |
| DOCX／XLSX／PPTX 内容读取 | 缺失，3 项 | 三者均返回 `unsupported`，正文为空 |
| CSV／TXT／文字型 PDF 读取 | 可用，3 项 | 能取回数据及预置内容标记 |
| 三种可编辑办公文件生成／修改路径 | 缺失，3 项 | 工具清单无写入／导出能力；模拟办公调用被拒绝为 `tool-forbidden` |
| 跨聊天读取办公附件 | 保护通过 | 拒绝访问不属于当前聊天的文件 |
| 临时聊天的 Office 附件保留 | 保护通过 | 关闭后无附件文件，持久数据无临时请求标记，禁止记忆访问 |

浏览器另行检查了 DOCX 上传和提交：有文件名、大小、删除附件和原件下载按钮；没有 Word 预览、原生编辑或新版本产物入口。上传时也没有提前提示“当前不能直接读取 Office”。浏览器使用的是原有本地回显模型，此项只证明 UI 路径，不用于判断 AI 质量。

### 缺口定位

- `packages/plugin/src/host/assets.ts:18`：Office 尚未识别为各自的 MIME 类型。
- `packages/plugin/src/host/assets.ts:56`：附件读取只有 PDF 与 UTF-8 路径，没有 OOXML 解析。
- `packages/plugin/src/host/service.ts:702`：工具只有读附件、可选联网、记忆；没有办公创建／修改／导出工具。
- `packages/plugin/src/client/Chat.tsx:10`：文件卡片只处理图片预览与原件下载，没有 Office 预览和产物版本。
- `.artifacts/office-baseline/runtime-results.json`：完整 14 项观察、实际工具与 Remote 清单。

## 可以复用 Harness 的渲染器，但要补齐结构与质量检查

已在安装版 **rc.3** 中实际调用公开的 `ctx.officeToPdf.convert()`，独立创建 Cordis 生命周期，不创建 Work Session，也不修改现用服务。三种文件都成功转换：

| 文件 | 输出 | 字体反馈 |
|---|---|---|
| Word | 1 页 PDF，49,857 字节 | 无缺失字体 |
| Excel | 3 页 PDF，33,461 字节 | Calibri 缺失 |
| PowerPoint | 2 页 PDF，34,080 字节 | Arial 缺失 |

已检查渲染图：Word 中文、表格可见；PPT 中文和两页内容完整；Excel 公式经渲染器重算后，预算 **230,000**、实际 **235,000**、差额 **5,000**、差额率 **2.17%** 正确。Excel 第五列被打印到第二页，说明 **转换成功不等于版面合格**，需要工作表原生预览与打印适配。不能用 PDF 文本提取替代单元格、公式和图表的结构化处理。

现有转换器会使用私有临时文件并有共享缓存。临时聊天不能直接共用这条会写临时文件的转换路径，也不能让临时产物进入共享缓存；办公执行必须有独立生命周期和经验证的 RAM 临时区／内存路径，否则该环境应明确拒绝临时 Office 任务，不能悄悄落盘。

rc.3 公共类型依据：`@deepseek-ai/dsh-office-to-pdf/lib/types/index.d.ts` 的 `convert` 与 `types.d.ts` 的字节来源接口。[上游接口说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/document/office-to-pdf/README.md)

## 推荐实施顺序

1. **共用办公文件管线**：产物身份和版本、受限的文件操作工具、可取消执行、预览与下载；沿用聊天归属和权限。不要给 Chat 开放宿主任意终端或文件系统。
2. **Word 完整闭环**：读取结构 → 生成报告 → 定点修改 → 页级预览 → 下载 DOCX。工程难度中等；复杂模板和修订保真更难。
3. **Excel 完整闭环**：多表、区域、公式重算、原生图表及结果核对。难度高；核心是数据与公式正确，不是表格外观。
4. **PPT 完整闭环**：可编辑对象、参考主题、单页修改及渲染检查。难度高；核心是版面和对象保真。
5. **联动与复用**：同一组数据生成 Word 报告、Excel 分析和 PPT 汇报；再加入模板库和区域批注。云端协作和加载项后置。

这条路线能留在单插件内。转换与文件库是内部实现依赖，用户不用手工搭配三个插件。真实模型对这些工具的使用、失败恢复和成品质量需在工具接通后验收；当前回显模型不能代替该项。

## 下一版的完成条件

- 一次提交预算数据，产出可打开且可编辑的 Word、PPT、Excel，并可在同一聊天继续修改。
- 三份文件的 230,000／235,000／5,000／2.17% 一致，Excel 中仍为公式与原生图表。
- “只改第二节／第二页／指定工作表区域”不改动无关部分，且原件不覆盖。
- 预览发现的溢出、遮挡、分页和缺失字体能够反馈并修复。
- 中断／重试不发布半成品；关闭临时聊天后没有其任务文件或缓存。
- 文档内容不自动升级为个人指令或记忆，不执行宏、外链或任意代码。
